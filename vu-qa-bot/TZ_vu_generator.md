**Заказчик:** Yanswap
**Назначение:** размеченный тестовый датасет для замера качества валидатора ВУ
**Версия:** 2.3 (бот сведён к одной команде /me; добавлен режим действующих прав)
**Связанный документ:** «ТЗ: система автоматической проверки ВУ РФ» (генератор обслуживает раздел 10 того ТЗ)

### Что изменилось в 2.3

| | 2.2 | 2.3 |
|---|---|---|
| Команды бота | `/me /region /birthplace /forget /gen /bad /case /mix /rules` | **только `/me`** (+ `/start`/`/help`), ФИО, ДР и место рождения вводятся одной строкой |
| Работа с датасетом | в боте и в CLI | **только CLI** (`vu_testdata.py`, `eval_rules.py`) |
| Срок действия | всегда случайный в допустимом интервале → ~2/3 записей просрочены | добавлен режим **`valid_now`**: срок ещё не истёк; бот использует его всегда |

**Почему появился `valid_now`.** По §4.4 дата выдачи распределена равномерно на всём интервале от `ДР+18` до `min(сегодня, ДР+60)`. Для человека 1983 г. р. это 2001–2026 гг., поэтому большинство записей получало срок, истёкший годы назад (замер: 127 из 200). Формально такая запись корректна и наш валидатор помечает её `green` — он проверяет консистентность оформления, а не действительность документа (§9). Но внешний проверяющий сервис отбраковывает её по сроку, и в датасете отсутствовал главный положительный кейс — действующие права. Режим `valid_now` смещает выдачу в интервал последних 10 лет, гарантируя `expiry > сегодня`.

## 1. Назначение и границы

Бот генерирует **синтетические записи ВУ** на основе личных данных, заданных пользователем, чтобы на них можно было измерить precision/recall движка правил валидации и держать регрессионный тест в CI.

### 1.1. Что бот делает

- по команде выдаёт запись, формально соответствующую всем правилам оформления ВУ;
- по команде выдаёт запись со **сломанным ровно одним правилом** и меткой, каким именно;
- выдаёт датасет файлом `.jsonl` с разметкой `expected_valid` / `broken_rule`.

### 1.2. Границы (не изменяются в 2.0)

Генератор производит **структурированные записи полей** (JSON), а не изображения документов и не бланки.

Каждая запись без исключений несёт признаки синтетики:
- поле `synthetic: true` — предикат `is_synthetic(rec)` истинен для **всех** записей (критерий приёмки 5);
- поля разметки `expected_valid` / `broken_rule` / `identity_source`, которых не существует в реальном потоке данных.

До версии 2.1 маркер жил также в серии (`00XX` — код, отсутствующий в справочнике ГИБДД). С 2.1 серия формируется из реального кода региона по требованию заказчика, поэтому признаком синтетики служат только метаполя.

Эти признаки — часть контракта датасета: по ним CI отличает тестовые записи от боевых. Удаление или подмена любого из них выводит артефакт за рамки настоящего ТЗ.

## 2. Источник личных данных

Личные данные записи — фамилия, имя, отчество, дата рождения — **задаются пользователем**. Генерация без них не поддерживается: `make_valid()` без `identity` бросает `ValueError`, бот отвечает подсказкой `/me`.

### 2.1. Профиль пользователя

Пользователь один раз задаёт свои данные командой `/me`, они сохраняются по его `user_id` и дальше используются во всех генерациях:

```
/me ЩЕРБАКОВ ДМИТРИЙ ВАЛЕНТИНОВИЧ 14.03.1988
```

- принимается 3 или 4 токена ФИО + дата `ДД.ММ.ГГГГ` последним токеном;
- отчество необязательно (3 токена = фамилия + имя + дата);
- регистр приводится к верхнему, буква Ё сохраняется (она значима для транслитерации);
- допустимые символы ФИО: русские буквы, дефис, пробел; иное — ошибка с пояснением;
- дата проверяется на существование и на то, что на **сегодня** исполнилось не менее 18 лет (иначе ВУ не могло быть выдано); верхняя граница — 100 лет;
- профиль хранится в `profiles.json` рядом с ботом, ключ — `user_id`, значение — ФИО, ДР, выведенный пол, дата сохранения;
- `/me` без аргументов показывает текущий профиль, `/forget` — удаляет.

Записи, построенные из профиля, помечаются `identity_source: "user"`.

### 2.2. Место рождения

Поле 3 (место рождения) задаётся пользователем командой `/birthplace` и хранится в профиле:

* свободный ввод: `/birthplace Г. ВОРОНЕЖ` — произвольный населённый пункт;
* быстрый выбор: `/birthplace` без аргументов показывает клавиатуру со справочником и кнопкой «🎲 Любое место»;
* нормализация: регистр к верхнему, схлопывание пробелов, Ё сохраняется;
* допустимые символы: русские буквы, цифры, пробел, дефис, точка, скобки; длина 2–60; хотя бы одна русская буква;
* пустое/пробельное значение трактуется как «не задано» — берётся случайное из справочника (это же поведение у CLI без `--birthplace`).

### 2.3. Разовые данные

Переопределение без сохранения профиля: `/gen ФАМИЛИЯ ИМЯ ОТЧЕСТВО ДД.ММ.ГГГГ`. Правила разбора те же.

Для CLI и CI, где интерактивного профиля нет, предусмотрен плейсхолдер `DEMO_IDENTITY_STR = "ТЕСТОВ ТЕСТ ТЕСТОВИЧ 01.01.1990"` — очевидно служебное значение, а не правдоподобное ФИО.

### 2.4. Пол

Пол **выводится из отчества**: окончания `-ОВНА/-ЕВНА/-ИЧНА/-ИНИЧНА` → женский, `-ОВИЧ/-ЕВИЧ/-ИЧ` → мужской. Если отчество не задано или окончание нераспознаваемо, пол берётся женским при окончании фамилии на `-А/-Я` (кроме `-ИНА`? нет: `-ИНА` тоже женское), иначе мужским. Пол сохраняется в профиле и на структуру записи не влияет.

### 2.5. Что НЕ меняется от источника данных

Всё остальное — серия, номер, даты выдачи и срока, категории, регион проживания, оборотная таблица, поле 14 — генерируется случайно по правилам раздела 4. Пользователь задаёт: поля 1, 2, 3 (ФИО, ДР, место рождения) и код подразделения в 4c, от которого зависит серия.

## 3. Модель записи

```python
@dataclass
class LicenceRecord:
    # лицевая сторона
    surname_ru: str; surname_lat: str          # 1
    given_ru: str;   given_lat: str            # 2 (имя + отчество)
    birth_date: str                            # 3, ДД.ММ.ГГГГ
    birth_place_ru: str; birth_place_lat: str  # 3
    issue_date: str                            # 4a
    expiry_date: str                           # 4b
    authority: str                             # 4c, "ГИБДД NNNN"
    series: str; number: str                   # 5, 4 + 6 цифр
    residence_ru: str; residence_lat: str      # 8
    categories: list[str]                      # 9
    # оборотная сторона
    back_table: dict[str, dict[str, str]]      # кат -> {open, expiry, restriction}
    back_number: str
    special_marks: str                         # 14
    # разметка датасета (в реальном потоке таких полей не существует)
    synthetic: bool = True
    expected_valid: bool = True
    broken_rule: str | None = None
    identity_source: str = "random"            # user | random   (новое в 2.0)
```

## 4. Правила генерации валидной записи

### 4.1. ФИО

Фамилия, имя, отчество берутся из профиля пользователя (раздел 2) без изменений; поле 2 (`given_ru`) склеивается как `ИМЯ ОТЧЕСТВО`.

Словари вымышленных ФИО удалены в версии 2.1. Покрытие «сложных» для транслитерации букв (Щ, Ё, Ъ, Ь, Ы, Ю, Я, Х, Ц, Ж, Ч, Ш, Й на конце, дефис) обеспечивают справочники места рождения и региона проживания, которые остаются словарными: например `Г. ЩЁЛКОВО`, `Г. ЮЖНО-САХАЛИНСК`, `Г. ЙОШКАР-ОЛА`, `ХАНТЫ-МАНСИЙСКИЙ АО - ЮГРА`.

### 4.2. Транслитерация

Все латинские строки вычисляются функцией по таблице приказа МВД / ИКАО Doc 9303:

```
А→A Б→B В→V Г→G Д→D Е→E Ё→E Ж→ZH З→Z И→I Й→I К→K Л→L М→M Н→N
О→O П→P Р→R С→S Т→T У→U Ф→F Х→KH Ц→TS Ч→CH Ш→SH Щ→SHCH
Ъ→∅ Ы→Y Ь→∅ Э→E Ю→IU Я→IA
```

Контрольные примеры: ДМИТРИЙ → DMITRII, МУРМАНСКАЯ → MURMANSKAIA, КРАСНОДАРСКИЙ → KRASNODARSKII, ЩЕРБАКОВ → SHCHERBAKOV, ПОДЪЯЧЕВ → PODIACHEV.

Транслитерируются: фамилия, имя+отчество, место рождения, регион проживания. Правило одинаково для словарных и пользовательских ФИО.

### 4.3. Дата рождения

ДР берётся из профиля (или из разовых данных). Проверки — по §2.1.

### 4.4. Даты выдачи и срока

- дата выдачи: случайная в интервале от `ДР + 18 лет` до `min(сегодня, ДР + 60 лет)`;
- **режим `valid_now`** (флаг `--valid-now`, в боте включён всегда): нижняя граница поднимается до `сегодня − 10 лет + 1 день`, верхняя равна сегодняшнему дню — срок действия гарантированно не истёк. По умолчанию режим выключен, чтобы датасет содержал и просроченные документы;
- дата выдачи **никогда не в будущем**;
- срок действия = дата выдачи + ровно 10 лет, тот же день и месяц;
- 29 февраля переносится на 28-е при сдвиге года.

### 4.5. Категории

Минимальный возраст на дату выдачи:

```
M, A1        → 16
A, B, B1, C, C1 → 18
BE, C1E, CE  → 19
D, D1, Tm, Tb → 21
DE, D1E      → 22
```

Обязательные зависимости (открыта слева → обязаны быть открыты справа):

```
B   → B1, M      A  → M       A1 → M
C   → C1, M      D  → D1, M
BE  → B, B1, M   CE → C, C1, M   C1E → C1, M
DE  → D, D1, M   D1E → D1, M
B1/C1/D1/Tm/Tb → M
```

Алгоритм: выбрать базовый набор (реалистичное распределение — чаще всего `B`, реже `B+C`, `A+B`, `D`, `B+BE`), взять транзитивное замыкание по таблице зависимостей, отфильтровать по возрасту, после фильтрации **повторно проверить замыкание** (если зависимость отпала по возрасту — убрать и зависящую категорию), в конце гарантировать `M`.

Допустимый алфавит — ровно 16 значений: `A A1 B B1 C C1 D D1 BE CE C1E DE D1E M Tm Tb`.

### 4.6. Регион и подразделение

Справочник — **полная таблица из 85 кодов** регионов ГИБДД с названиями в том виде, как печатаются на бланке («КРАСНОДАРСКИЙ КР.», «МУРМАНСКАЯ ОБЛ.», «Г. МОСКВА»). Отсутствующие в таблице коды (`00, 20, 80, 81, 84, 85, 88, 90, 91, 93, 94, 96–99`) считаются невалидными и используются мутатором R07.

**Выбор подразделения.** Пользователь выбирает код командой `/region` (инлайн-клавиатура с пагинацией, 24 кода на страницу, кнопка «🎲 Любое подразделение» сбрасывает выбор). Выбор хранится в профиле и применяется ко всем последующим генерациям. Если не выбран — код берётся случайно из справочника.

- поле 4c: `ГИБДД` + 4 цифры, первые две — код выбранного подразделения, вторые две — случайные `00–99`;
- поле 8: регион проживания;
- в **85% случаев** регион проживания в п. 8 совпадает с регионом подразделения из 4c, в 15% — намеренно различается. Это валидная ситуация: с 2017 года ВУ получают в любом регионе независимо от прописки. Записи с расхождением остаются `expected_valid: true` и служат тестом на то, что валидатор не переводит это правило в отказ;
- место рождения (п. 3) задаётся пользователем (§2.2) и не связано с регионом проживания; если не задано — случайное из справочника.

### 4.7. Серия и номер

- серия: **код региона подразделения** (первые две цифры поля 4c) + две случайные цифры; тем самым серия и подразделение всегда согласованы;
- номер: 6 случайных цифр с ведущими нулями;
- поле `back_number` = `"{серия} {номер}"`, посимвольно совпадает с полем 5.

### 4.8. Оборотная таблица

Строка на каждую открытую категорию, ключи строго равны множеству `categories`:
- `open` = дата выдачи; в ~25% случаев для категорий A/A1/M дата открытия ставится раньше (например, на 3 года), но не раньше достижения минимального возраста;
- `expiry` = дата в поле 4b;
- `restriction` — в ~12% случаев код из `AT`, `AS`, `MS`, `ГБО`, иначе пусто.

### 4.9. Поле 14

Год первого получения прав = минимальный год среди дат открытия в оборотной таблице. Всегда ≤ года выдачи.

### 4.10. Автопродление 2022–2025

Отдельная публичная функция, которую использует и генератор, и валидатор:

```python
def effective_expiry(expiry: date) -> date:
    if date(2022, 1, 1) <= expiry <= date(2025, 12, 31):
        return plus_years(expiry, 3)
    return expiry
```

Права со сроком, истекающим с 01.01.2022 по 31.12.2025, действительны ещё три года от даты окончания. Само автопродление отменено с 01.01.2026, но выданные в это окно документы продолжают действовать.

Датасет обязан **естественным образом** содержать такие записи (они появляются сами при случайном выборе даты выдачи) — это тест на то, что валидатор не отбраковывает действующие права.

## 5. Мутаторы

Каждый мутатор берёт валидную запись и ломает **ровно одно** правило, возвращая запись с `expected_valid: false` и `broken_rule: <имя>`.

| Имя | Что ломает | Как |
|---|---|---|
| `translit_mismatch` | R01 | Наивная транслитерация: `KH→H`, `IA→YA`, `Й→Y` — типовая ошибка подделки |
| `expiry_not_plus_10y` | R02 | Срок = выдача + 5/9/11/15 лет |
| `front_back_number_mismatch` | R03 | Одна цифра в `back_number` сдвинута на +1 |
| `category_dependency_broken` | R04 | Удалить категорию, **от которой зависит другая открытая** (BE без B, B без B1) |
| `front_back_category_mismatch` | R05 | Добавить категорию в п. 9, не добавляя строку на оборот |
| `underage_at_issue` | R06 | Сдвинуть ДР так, чтобы возраст был на 1–3 года ниже порога строжайшей категории |
| `invalid_authority_region` | R07 | Код региона вне справочника |
| `unknown_category_symbol` | R08 | Добавить `E`, `B2`, `CD`, `A2` |
| `issue_date_in_future` | R09 | Дата выдачи на 30–900 дней вперёд |
| `special_marks_after_issue` | R10 | Год в поле 14 на 1–5 лет позже выдачи |
| `back_open_after_expiry` | R11 | Дата открытия одной категории — позже срока действия |

**Критично для `category_dependency_broken`:** нельзя удалять произвольную категорию. Если удалить ту, от которой ничего не зависит (например `A` из набора `A, B, B1, M`), останется формально консистентный набор, и кейс станет ложно-негативным. Удалять только из числа категорий, входящих в `IMPLIES` какой-либо другой открытой категории; при отсутствии таких — подставить набор `["BE"]` без базовой `B`.

**Общее требование ко всем мутаторам:** ломается ровно одно правило. Побочные поля приводятся в согласованное состояние (например, `expiry_not_plus_10y` синхронно правит `expiry` в оборотной таблице, `issue_date_in_future` сдвигает и выдачу, и срок, `category_dependency_broken` пересчитывает поле 14) — иначе запись нарушит два правила сразу и перестанет быть точечным тестом.

**Мутаторы в режиме профиля.** `underage_at_issue` по своей природе меняет дату рождения, то есть расходится с профилем пользователя. Это допустимо и ожидаемо: мутированная запись — заведомо невалидный тестовый артефакт, а не документ пользователя. Признак `identity_source` при этом сохраняется.

Мутаторы регистрируются в словаре через декоратор, чтобы добавление нового не требовало правок в других местах.

---

## 6. Требования к случайности

- источник энтропии создаётся **на каждый запрос** (`random.Random(secrets.randbits(64))`), а не один раз при старте процесса;
- ФИО и ДР фиксированы намеренно (они заданы пользователем) — уникальность записи обеспечивают серия и номер; тест проверяет 50 уникальных пар (серия, номер) в пакете из 50;
- CLI-режим поддерживает `--seed` для воспроизводимых прогонов в CI; в боте seed не задаётся.

## 7. Telegram-бот

**Стек:** Python 3.11+, aiogram 3.x, long polling.

### 7.1. Доступ

Список разрешённых `user_id` из переменной окружения `ALLOWED_USERS` (через запятую). **Без неё бот не стартует** — падает с внятным сообщением. Сообщения от посторонних игнорируются молча, без ответа.

### 7.2. Команды

| Команда | Поведение |
|---|---|
| `/start`, `/help` | Баннер, формат ввода, текущие сохранённые данные |
| `/me` | Без аргументов — показать сохранённое и клавиатуру подразделений |
| `/me ФАМИЛИЯ ИМЯ [ОТЧЕСТВО] ДД.ММ.ГГГГ [МЕСТО РОЖДЕНИЯ]` | Единственная рабочая команда: разбирает строку, сохраняет и предлагает выбрать подразделение |

Разбор строки: дата в формате `ДД.ММ.ГГГГ` служит разделителем — всё до неё ФИО (2–3 слова), всё после — место рождения (может отсутствовать → случайное из справочника).

После выбора подразделения на инлайн-клавиатуре (85 кодов, пагинация, «🎲 Любое подразделение») бот выдаёт одну запись в режиме `valid_now`.

**Работа с датасетом вынесена в CLI.** Битые записи, мутаторы, `.jsonl` и метрики доступны через `vu_testdata.py` и `eval_rules.py`; в боте их нет.

### 7.3. Профиль

Хранится в `profiles.json` рядом с ботом: `{ "<user_id>": {"surname","name","patronymic","birth_date","gender","region","birth_place","saved_at"} }`. Смена подразделения не затирает ФИО и наоборот. Запись атомарная (временный файл + `os.replace`). Профиль одного пользователя невидим другим.

### 7.4. Текстовый формат вывода

Моноширинный блок, порядок полей повторяет бланк: баннер, поля 1–9, разделитель, оборотная таблица (только открытые категории, в порядке `ALL_CATEGORIES`), поле 14, номер, служебный блок (`synthetic`, `is_synthetic(rec)`, `identity_source`, `expected_valid`, `broken_rule`, `effective_expiry` — последнее только если отличается от 4b).

### 7.5. Формат файла

`.jsonl`, одна запись на строку, UTF-8 без экранирования кириллицы (`ensure_ascii=False`). Имя файла: `dataset_{ok}_{bad}.jsonl`. В подписи к документу — баннер и счётчики.

## 8. CLI

Тот же генератор должен работать без Telegram:

```
python vu_testdata.py --valid 500 --mutated 1100 --seed 7 -o dataset.jsonl
python vu_testdata.py --valid 10 --identity "ЩЕРБАКОВ ДМИТРИЙ ВАЛЕНТИНОВИЧ 14.03.1988" \
    --region 77 --birthplace "Г. ВОРОНЕЖ"
```

`--region` принимает код из справочника; неизвестный код — выход с кодом 2. Без `--identity` подставляется плейсхолдер `DEMO_IDENTITY_STR`.

Это точка входа для CI.

## 9. Тесты и критерии приёмки

1. Для каждой валидной записи `translit(surname_ru) == surname_lat` (и так для всех четырёх пар полей).
2. Для каждой валидной записи выполняются все правила раздела 4: срок = выдача + 10 лет, замыкание категорий, возрастные пороги, `back_table.keys() == set(categories)`, `back_number == "{series} {number}"`, поле 14 ≤ года выдачи.
3. Каждый мутатор на 100 прогонах даёт запись, которую эталонный валидатор помечает `red` — **100/100, ложно-негативных нет**.
4. В пакете из 50 записей — 50 уникальных пар (серия, номер) при неизменных ФИО и ДР.
5. `is_synthetic(rec)` возвращает `true` для **всех** записей без исключения (проверяется и на объекте, и на его `dict`).
6. Бот не стартует без `ALLOWED_USERS`.
7. Записи из профиля: поля 1, 2, 3 совпадают с профилем посимвольно; `identity_source == "user"`; все правила п. 2 соблюдены.
7a. При выбранном подразделении: первые две цифры серии равны коду в поле 4c; код вне справочника и генерация без личных данных дают `ValueError`.
7b. Заданное место рождения попадает в поле 3 без искажений (после нормализации), латиница = `translit(place)`; недопустимая строка даёт `IdentityError`, пустая — фолбэк на справочник.
7c. `parse_me()` разбирает строку `/me` по дате-разделителю; при `valid_now=True` на 200 прогонах ни одной записи с истёкшим сроком, при выключенном режиме просроченные встречаются.
8. Прогон `eval_rules.py --valid 500 --mutated 1100` завершается с кодом 0.

Пункты 5 и 7 проверяются на приёмке отдельно, чтением кода, а не только тестами.
